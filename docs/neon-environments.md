# Neon production and development databases

The existing Neon project `indrax` (`shy-moon-69793353`, AWS US East, Postgres 17)
uses production as its default root branch and develop as a long-lived child.
This follows Neon's [production/staging workflow](https://neon.com/branching/production-staging-workflows).
Git branches and Neon branches are separate: merging Git code never merges database data.

| Environment           | Git branch | Neon branch                                 | Database | Runtime role     | Worker       |
| --------------------- | ---------- | ------------------------------------------- | -------- | ---------------- | ------------ |
| Production            | `main`     | `production` (`br-sparkling-moon-ahxrfmpy`) | `indrax` | `indrax_app`     | `indrax`     |
| Development / staging | `develop`  | `develop` (`br-cool-meadow-ahq7py8f`)       | `indrax` | `indrax_dev_app` | `indrax-dev` |

Each environment has its own compute endpoint and independent application password.
Runtime connections use the transaction pooler; migrations use the direct endpoint
with `neondb_owner`. Application roles can read and modify app tables, but cannot
create schema objects, create databases/roles, bypass RLS, or access the Drizzle
migration journal. Default privileges grant app DML access to future public tables
created by the migration owner. The existing self-managed Better Auth and GitHub
OAuth use the app's public auth tables; the unrelated `neon_auth` schema in the
default production `neondb` database is not used by this application.

## Local credential reference

Real connections are saved only in the ignored `.env.neon` file, with permissions
`0600`. Its keys are deliberately unique so loading it cannot silently replace
development's `DATABASE_URL` with production's URL:

- `DATABASE_URL`: develop runtime connection, also suitable for explicitly selected local development.
- `DEVELOP_ADMIN_DATABASE_URL`: original develop dashboard connection, preserved.
- `DEVELOP_DIRECT_DATABASE_URL`: develop migration connection.
- `PRODUCTION_DATABASE_URL`: production runtime connection to `indrax`.
- `PRODUCTION_DIRECT_DATABASE_URL`: production migration connection to `indrax`.
- `PRODUCTION_ADMIN_DATABASE_URL`: original production dashboard connection to `neondb`, preserved as supplied.

The app and migration tooling do not automatically load `.env.neon`. Local Docker
configuration in `.env.local` remains independent. Never copy production credentials
into client variables, fixtures, examples, or committed files. Set the intended
environment's runtime connection as the Worker's `DATABASE_URL` secret. Runtime
secrets do not need migration-owner credentials.

For an explicitly selected production migration, pass both database variables so
the tooling cannot fall back to a local `DIRECT_DATABASE_URL`:

```bash
node --input-type=module -e '
process.loadEnvFile(".env.neon");
const { spawnSync } = await import("node:child_process");
const env = {
  ...process.env,
  DATABASE_URL: process.env.PRODUCTION_DATABASE_URL,
  DIRECT_DATABASE_URL: process.env.PRODUCTION_DIRECT_DATABASE_URL,
};
if (!env.DATABASE_URL || !env.DIRECT_DATABASE_URL) throw new Error("Production URLs are missing");
const result = spawnSync("npm", ["run", "db:migrate"], { env, stdio: "inherit" });
process.exit(result.status ?? 1);
'
```

For development migrations, select `DATABASE_URL` and `DEVELOP_DIRECT_DATABASE_URL`
instead. Keep schema changes in the existing Drizzle migration files; review their
SQL, test them on an isolated branch, and apply the same files to production after
release approval. Avoid `db:push` and untracked manual schema changes.

## Branch lifecycle and release preparation

Keep production as the schema source for future preview/test branches. Branches
inherit their parent's schema and data at creation, then evolve independently.
Existing develop predates this setup and has its own authored content: do not reset
it to production without an explicit decision to discard or preserve those changes.
Production auth tables contain identity/session data after login; use a schema-only
or anonymized branch for future tests that do not need real production data.
Do not copy production sessions into a shared development environment.

Use expiring branches for migration experiments. Before each production migration,
verify the target branch/database, inspect pending migration SQL, test on a child,
and record a restore point within the available history window. For durable backups,
use the direct owner connection with `pg_dump` and store the export privately.
Restore into a separate branch and validate it before changing a Worker connection.
Worker rollback changes code, not database schema or data; keep schema changes
compatible with the previous deployed code and prepare recovery for destructive migrations.

The current Neon Free plan rejects branch protection and configurable suspension
intervals. No paid upgrade was performed. Before launch, decide whether to upgrade
for production branch protection and a longer recovery window. Protection prevents
branch deletion/reset and regenerates passwords on newly created children; it does
not remove the need for distinct runtime credentials and careful migration review.

Production GitHub OAuth app creation and its client credentials remain with the
owner. Its callback is `https://indrax.uk/api/auth/callback/github`. Review and approve
the separate `develop` → `main` release PR before the gated production deployment.
